# RUNBOOK — эксплуатация tgfarm

Что делать, когда что-то пошло не так. Каждая процедура начинается с диагностики.

---

## 1. Ежедневный контроль

```bash
tgfarm doctor                    # конфиг, БД, эмбеддер, LLM, telegram
tgfarm status                    # объём накопленного, режим, can_publish
tgfarm report --days 7           # ERR/ER по углам и часам
tgfarm channels                  # нагрузка по каналам за сегодня
tgfarm posts --status rejected   # что и почему отклонено
```

Или открыть панель: `tgfarm serve` и `http://localhost:8000/`. Там же видно
формат каждого поста, обложки, состояние конвейера по стадиям и то, что
конкретно отказал лицензионный фильтр видео.

Тревоги ( Grafana + Prometheus):

| Метрика | Порог | Действие |
|---|---|---|
| `last_successful_post` | > 12 ч | цикл встал — проверить `GET /api/runs` |
| `posts_published_24h` | < 60% от плана | скорее всего упал heat или источники |
| `reject_rate` | > 50% | сломался промпт или персона |
| `source.failures` | ≥ 3 | источник отключить в `config/sources.yaml` |
| `posts.total / published` | расходится > 20% | копится черновиков — смотреть S5 |

## 2. Ферма молчит (нет постов)

```bash
tgfarm trends                    # есть ли горячие кластеры?
tgfarm sources                   # здоровье источников
```

**Кластеров нет** → источники молчат или не отвечают.

```bash
tgfarm collect --all             # принудительно, минуя min_interval_s
```

Дальше по логам: `collector <id> failed: <ошибка>`. Типовые причины — 404 у
источника, смена URL RSS, rate limit. Выключить битый источник, починить в YAML.

**Кластеры есть, `heat` ниже 0.62** → порог слишком высокий для текущего потока.

```yaml
# .env
HEAT_THRESHOLD=0.50
```

**Кластеры горячие, но постов нет** → проверьте не порог, а квоту и форматы:

```bash
tgfarm channels                   # posts_per_day и posts_today по каналам
tgfarm posts --limit 50           # что застряло: draft / gated / rejected
```

Частая причина — длинный формат у короткого канала. `tech_deep_ru` публикует
`article` на 1200–2500 символов; остальные восемь каналов ограничены 500–1100 и
S10 понижает их до `news`. Если канал внезапно перестал выпускать текст,
посмотрите `max_chars` в `config/personas.yaml`.

Если опустить пришлось до <0.45 — проблема не в пороге, а в том, что ферма не
собирает достаточно источников на нишу. Добавьте источники, а не снижайте порог.

**Кластеры `ready`, черновиков нет** → routing. `s3_route: 0 -> 0` в логах.
Проверить: есть ли включённый канал для ниши кластера и не выбита ли дневная квота.

## 3. Всё отклоняется

```bash
tgfarm posts --status rejected --limit 50
```

В `reject_reason` всегда есть гейт и причина.

| Гейт | Почти наверняка | Что делать |
|---|---|---|
| `length` | персона требует больше, чем есть в источнике | снизить `min_chars` или добавить источники с длинным текстом |
| `facts` | LLM выдумывает числа | проверить фактчек на глаз, при необходимости ужесточить `MIN_VERIFIED_RATIO` |
| `vocabulary` | запрещённые слова в `banned_words` | пересмотреть список персоны — он часто устаревает |
| `tone` | критика ниже 7 | посмотреть, что именно он ругает, и поправить `style_notes` |
| `uniqueness` | канал исчерпал тему | это нормально: 72-часовой cooldown. Проверить, не генерируется ли одно и то же |
| `copyright` | тело повторяет заголовок | прокрутить источник — возможно, фид отдаёт только заголовок |

Если после рерайта всё равно `rejected` — смотрите `POST /api/posts/{id}`,
поле `quality.reason`. Это точная причина, а не категория.

**Внезапно 100% отклонений при неизменном конфиге** — почти всегда поломался LLM
и сработал офлайн-композер: он берёт первые предложения источника, и они не
проходят гейты. Проверьте `tgfarm doctor` → строка `llm`.

## 4. Посты не публикуются

```bash
tgfarm status | jq .can_publish
```

`can_publish: false` означает: режим не `live`, **или** нет `TELEGRAM_BOT_TOKEN`,
**или** нет `TELEGRAM_CHANNELS`.

Порядок проверки:

1. `TGFARM_MODE=live` в `.env`
2. Бот добавлен в канал **администратором** с правом «Публикация сообщений»
3. `TELEGRAM_CHANNELS=-1001234567890` — числовые id со знаком минус
4. `tgfarm doctor` → строка `telegram`, поле `username`

**`FloodWait`** при отправке: Bot API даёт 30 сообщений/с; в `ratelimit.py` стоит
25/с. Если ловите `RetryAfter` — снишайте `RATE.bot_api` в коде, а не обходите
ошибку.

**`Chat not found`** — бот не администратор канала. Проверить через `@getmyupdates`
или просто посмотреть список участников канала вручную.

**Посты висят `scheduled` и не уходят** — слот не наступил. `tgfarm posts` покажет
`scheduled_at`. Если все слоты в прошлом, проверьте `TZ` в `.env`: планировщик
считает часы в нём.

## 5. Канал забанили

1. **Остановить** (`tgfarm` в терминале — Ctrl+C). Не перезапускать против того же токена.
2. Проверить ограничения у `@SpamBot`.
3. Логи: `tgfarm`, последние строки перед баном.

Ферма не делает ничего, что должно вызвать бан. Наиболее вероятные причины:

- **Слишком много каналов с одного аккаунта-бота.** Один бот администрирует все
  каналы фермы. Telegram это видит, и при жалобах в сети пострадают все сразу.
  → Решение: **один бот на 2–3 канала**, отдельные номера.
- **Плагиат.** Пост, воспроизводящий чужой заголовок. Гейт `copyright` ловит это,
  но если рерайт его проигнорировал — смотреть вручную.
- **Спам в ссылках.** Три ссылки на источник в каждом посте выглядят нормально;
  пять — нет. Держать `max_sources: 3`.

**Если аккаунт ограничен (не забанен):** поставить паузу на сутки, не отправлять
ничего, затем перейти на другого бота. Угрожать Telegram репутацией после бана
бессмысленно.

## 6. Контент не заходит

```bash
tgfarm report --days 14
```

Ключи в ответе: `angles` (ER по углам) и `hours` (ER по часам).

**ER ниже 3% во всех углах** → проблема не в формате, а в содержании. Проверить:
- первые 5 постов канала (новый читатель решает по ним)
- закреп и описание канала
- соответствие заголовка канала тому, что внутри

**Один угол работает лучше** → поднять его вес в `angle_weights` персоны.
Эти веса сэмплируются в `Persona.sample_angle`, поэтому правка сразу в силе.

**Один час работает лучше** → `config/slots.yaml`, `hour_weights`. Ферма
подхватит на следующем цикле.

**Просмотры падают при росте подписчиков** → классическая картина накрутки или
мёртвой аудитории. Проверить соотношение просмотров к подписчикам: ниже 20% —
канал мёртв для рекламодателя, пора чинить, а не масштабировать.

## 7. Обслуживание

### Приложение не запускается второй раз

Так и задумано: в `data/desktop.lock` лежит pid работающей копии. Два
планировщика на одном наборе каналов дрались бы за слоты и квоты.

```powershell
Get-Process TgFarm                     # найти живой процесс
Stop-Process -Name TgFarm              # снять его
Remove-Item data\desktop.lock          # только если процесса точно нет
```

Если файл остался после краша, новый запуск подхватит его сам: pid
проверяется на живость.

### Панель открывается пустой, API отдаёт 401

Ожидаемо: `/api/*` требует токен.

```bash
tgfarm status                                   # работает без токена
curl -H "X-TGFarm-Token: $(cat data/api_token)" localhost:8000/api/status
```

Страница подставляет токен сама. Если открываете API руками из Postman или
Insomnia — берите заголовок из `data/api_token`. Токен можно зафиксировать в
`.env` (`TGFARM_API_TOKEN=...`) или отключить защиту на доверенной машине
(`TGFARM_REQUIRE_TOKEN=false`) — но не на машине с доступом в интернет.

### Забыли пароль от панели

Пароля нет: это локальный токен, а не учётная запись.

```bash
python -c "from tgfarm.core.apiauth import rotate_token; print(rotate_token())"
```

### Схема и миграции

`create_all()` создаёт только *таблицы*: колонка, добавленная в модель после
развёртывания, в уже существующей базе не появится, и каждый запрос к ней
упадёт с «no such column». Поэтому при каждом старте `init_db()` сверяет
метаданные с живой схемой и добавляет недостающие колонки через
`ALTER TABLE ... ADD COLUMN` (`db/bootstrap.py:apply_additive_migrations`).
Миграция идемпотентна и безопасна на SQLite и Postgres.

Что она **не** делает: удаления, переименования, смены типов и NOT NULL на
заполненной таблице. Это уже работа настоящего инструмента миграций — если
такое понадобится, сначала сделайте бэкап.

### Обновление

```bash
git pull
pip install -e .
tgfarm init          # применит новые колонки
tgfarm repair        # перерисует пропавшие обложки, почистит orphan-медиа
tgfarm doctor        # убедиться, что конфиг и провайдеры живы
tgfarm demo          # конвейер должен пройти целиком
```

### Переезд на другой ПК

```powershell
# из старой установки
robocopy data D:\tgfarm-data /E
robocopy config D:\tgfarm-config /E
copy .env D:\tgfarm.env
# в новой
copy D:\tgfarm-data\* <папка>\data\ /S
copy D:\tgfarm-config\* <папка>\config\ /S
copy D:\tgfarm.env <папка>\.env
```

`config/` в собранном `.exe` создаётся сам при первом запуске — это копия
поставляемых настроек, её и нужно править.

### Видео: сколько стоит фильтр лицензий

Если видео включено, но в постах его нет — сначала посмотрите, что именно
отказал гейт:

```bash
curl -s localhost:8000/api/status | jq '.capabilities.video'
tgfarm serve && grep "video refused" logs/*.log | tail -50
```

Типичные причины: видео лежит на видеоплатформе (отказ всегда), чужой домен без
пометки CC, файл больше `VIDEO_MAX_MB` или длиннее `VIDEO_MAX_DURATION_S`.
Это ожидаемое поведение: снять фильтр можно только `VIDEO_ALLOW_UNKNOWN=1`, и
это решение владельца канала, а не настройка фермы.

### Обслуживание LLM

```bash
curl -s localhost:8000/api/models | jq
```

`zen_token: false` означает, что ключ не задан — в этом случае Zen пропускается
без единого запроса, и генерация идёт через следующего провайдера в цепочке.
Если при заполненном ключе текст всё равно идёт от офлайн-композера, смотрите
`llm_stats` в выводе `tgfarm doctor`: там видно, сколько раз каждый провайдер
упал.

### Бэкап

```bash
# SQLite
sqlite3 tgfarm.db ".backup 'backup/tgfarm-$(date +%F).db'"
# Postgres
pg_dump -Fc tgfarm > backup/tgfarm-$(date +%F).dump
tar czf backup/media-$(date +%F).tgz data/media
```

Восстановление **обязательно проверять** хотя бы раз в месяц:

```bash
cp backup/tgfarm-2026-10-01.db tgfarm.db
tgfarm status     # должно открыться и показать счётчики
tgfarm demo       # конвейер должен отработать на восстановленной базе
```

Бэкап, который не восстанавливали, — это не бэкап.

### Ротация

```yaml
# .env
MAX_AGE_DAYS=21              # в s1_sources, режет старые items
```

Рост базы: ~1–3 тыс. items/сутки на 20 источников, ~30 постов/сутки.
Postgres спокойно живёт год без vacuum, SQLite — дольше при `WAL`.

### Переход на Postgres

```yaml
DATABASE_URL=postgresql+psycopg://tgfarm:tgfarm@localhost:5432/tgfarm
```

Схема совместима. Пересоздать:

```bash
tgfarm init            # create_all, безопасно для существующих данных
```

Масштабирование: `DATABASE_URL` на управляемый Postgres, `docker compose up`.
Переход на pgvector — при >1 млн items, правка `db/vector.py` целиком.

## 8. Почему нет комментинга и посевов

Зафиксировано, потому что это будет спрашивать каждый, кто читает код.

Заявленная методика — «комментинг с множества аккаунтов, реакция, потом
комментарий со ссылкой». Разбор по шагам:

| Примитив | Реализация в ферме | Почему |
|---|---|---|
| Нейро-комментарии со ссылкой | ❌ | Работает, но 1 аккаунтом и вручную. Масштабируется только через спам. |
| Автопрогрев аккаунтов | ❌ | Вендоры сами пишут: «прогрев не снимает ограничения и не гарантирует, что модуль отработает без отказов». |
| Реакции → комментарий | ❌ | Такой фичи нет. Есть связка «комментарий + лайкер». |
| Масс-инвайт / рассылка в личку | ❌ | Прямой запрет Пользовательского соглашения. Перманентный бан. |
| Кросспост через официальные API | ✅ | Полностью автоматизируется, риска нет. |

Экономика, ради которой всё это и рассматривалось (замеры 2026):

| Метод | Подписчиков/мес | Прямые затраты | CPA |
|---|---|---|---|
| Взаимопиар | 4 500–14 000 | 0 ₽ | **0–10 ₽** |
| Telegram Ads (реселлер) | 6 000–20 000 | 30 000 ₽ | 50–300 ₽ |
| Комментинг, 1 живой аккаунт | ~600 | 0 ₽ (время) | 0 ₽ |
| Фарм комментариев (100 акк.) | 2 000–6 000 | 25 000–70 000 ₽ | 195–580 ₽ |

Взаимопиар дешевле в 20–60 раз и не несёт риска бана. Фарм комментариев — это
не более эффективный канал, а **закупка аккаунтов**, которая нужна только чтобы
обойти блокировку, которую сама же и создаёт.

Плюс: массовые рассылки нарушают соглашение Telegram (ст. 4.1 — блокировка без
компенсации), а координатированные комментарии с фейковых аккаунтов — это
введение в заблуждение (ст. 14.1 КоАП РФ, DSA в ЕС).

**Что сделано вместо:** кросспост через официальные API, автоподбор
взаимопиара (S9, очередь на вычитку), SEO-генерация, бот-воронка. Всё
автоматизируется и не нарушает ничего.

## 10. Полезные запросы к базе

```sql
-- что публикуется
SELECT channel_id, COUNT(*) FROM posts
 WHERE status='published' AND published_at > now() - interval '7 days'
 GROUP BY channel_id;

-- причины отклонений
SELECT reject_reason, COUNT(*) FROM posts
 WHERE status='rejected' AND created_at > now() - interval '7 days'
 GROUP BY reject_reason ORDER BY 2 DESC;

-- горячие кластеры прямо сейчас
SELECT public_id, label, niche, ROUND(heat::numeric,3) AS heat, item_count
  FROM clusters WHERE status='ready' ORDER BY heat DESC LIMIT 20;

-- источники-отники
SELECT id, failures, last_error FROM sources
 WHERE failures >= 3 ORDER BY failures DESC;

-- частота по часам (должна совпадать с пиком)
SELECT EXTRACT(hour FROM published_at) AS h, COUNT(*)
  FROM posts WHERE status='published' GROUP BY h ORDER BY h;

-- какие форматы реально публикуются (должен быть разброс, а не один формат)
SELECT post_format, channel_id, COUNT(*), ROUND(AVG(LENGTH(body))) AS avg_len
  FROM posts WHERE status='published' AND created_at > now() - interval '7 days'
  GROUP BY post_format, channel_id ORDER BY 3 DESC;

-- что пришло с видео прямо сейчас
SELECT source_id, title, media_kind, media_links FROM raw_items
 WHERE media_kind IS NOT NULL ORDER BY fetched_at DESC LIMIT 20;

-- посты, которые застряли дольше суток
SELECT public_id, channel_id, status, created_at FROM posts
 WHERE status IN ('draft','gated') AND created_at < now() - interval '1 day'
 ORDER BY created_at LIMIT 50;
```
