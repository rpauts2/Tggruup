# Контролируемый smoke-test VK и Дзена

Цель: проверить реальные маршруты доставки так, чтобы тест сам не создал волну дублей или лишних публикаций. Автоматические тесты не заменяют этот прогон: он выполняется только на твоих авторизованных аккаунтах и в твоём тестовом канале.

## 0. Безопасная подготовка

1. Обнови проект и запусти из его виртуального окружения.
2. Сделай и проверь локальную копию базы: `tgfarm backup`. Команда должна вернуть `verified: true` и `integrity_check: "ok"`.
3. Запусти `tgfarm doctor`. Исправь ошибки конфигурации, БД, Telegram и сессии Дзена до публикации.
4. Убедись, что `TGFARM_MODE=dry` или `off` используется для обычной отладки. Live-режим включай только для отдельного контролируемого прогона.
5. Используй отдельный тестовый канал/сообщество, где допустимы тестовые записи. Не начинай с массовой очереди.

Для offline end-to-end прогона без реальных публикаций:

```bash
tgfarm demo --cycles 1
tgfarm status
tgfarm report --days 7
```

Команда `tgfarm demo` принудительно переводит настройки процесса в режим `off` на время прогона и восстанавливает исходный режим в `finally`. Поэтому она не должна отправлять синтетические посты даже при `TGFARM_MODE=live` в `.env`. В CI отдельно закреплён тест этого защитного поведения. Сам smoke-прогон сохраняет в базе синтетические материалы, поэтому для оценки метрик на рабочей БД предпочтительна отдельная копия базы.

## 1. VK

Сначала проверь один материал с обложкой, затем отдельный материал без изображения. Не меняй и не подставляй неправильный токен в production-конфигурации: сценарии 401/429/500/timeout уже моделируются автоматическими тестами, а живой прогон должен проверять корректную авторизацию.

Для каждого теста:

1. Возьми один короткий тестовый материал с ясным заголовком и ссылкой на источник.
2. Включи live-режим только на время теста и отправь ровно одну публикацию.
3. Открой целевую стену VK вручную и проверь текст, ссылки, хештеги, обложку и фактический URL.
4. Сверь URL/remote ID и последнюю запись кросспоста в панели или журнале.
5. Перезапусти ферму и убедись, что тот же кросспост не отправился повторно.
6. Если статус `unknown`, сначала найди публикацию на стене и используй действие подтверждения результата. Не разрешай повтор, пока вручную не проверено отсутствие поста.

Успешный результат: один удалённый пост соответствует одной локальной записи со статусом `posted`, известным remote ID/URL и корректной обложкой (если она была).

## 2. Дзен

1. Проверь сессию через `tgfarm doctor`; если нужно, выполни `tgfarm dzen-login` и войди вручную.
2. Отправь один тестовый материал с обложкой, затем другой без неё. Не используй тесты с большим объёмом публикаций.
3. Проверь заголовок, тело, размещение изображения, форматирование и URL опубликованного материала.
4. Проверь результат в панели и журнале: публикация должна быть связана с локальной записью.
5. Если редактор завис, вернул ошибку или соединение оборвалось после нажатия публикации, сначала проверь канал в браузере. Не нажимай повтор автоматически при неизвестном результате.
6. Если появилась проверка CAPTCHA, останови поток и пройди её вручную в открытом браузере. Не пытайся обходить проверку кодом.

## 3. Поведение при сбоях

| Сценарий | Где проверять | Ожидаемое поведение |
|---|---|---|
| Нет токена/сессии | offline-тесты и `doctor` | понятное предупреждение; не маскировать как успешную публикацию |
| HTTP 429 | автоматический тест адаптера | ограниченный повтор после задержки |
| 4xx, кроме retryable-кодов | автоматический тест адаптера | постоянная ошибка; вмешательство оператора после исправления конфигурации |
| Тайм-аут чтения/ответа | автоматический тест + live сверка | `unknown`; без автоматического повтора |
| Перезапуск после отправки | локальная БД + удалённая площадка | существующая публикация не отправляется повторно |
| Сбой процесса до подтверждения | watchdog и журналы | задача возвращается в понятное состояние, неизвестное внешнее действие требует сверки |

Не моделируй тайм-аут отключением сети посреди реальной отправки. Для этого есть детерминированные тесты с поддельным HTTP-ответом.

## 4. Контрольная ведомость

Веди короткую запись на каждый тест: дата/время, платформа, локальный ID, remote ID/URL, статус до и после перезапуска, обложка да/нет, результат и ссылка на лог. Для каждого канала сначала добейся серии чистых единичных проверок, затем увеличивай объём постепенно. Критерий из roadmap: не менее 10 контролируемых успешных публикаций на VK и отдельно на Дзене без необъяснимых пропусков/дублей, при соблюдении ограничений площадки.

## 5. Когда считать этап закрытым

- [ ] Оффлайн CI зелёный, включая end-to-end demo.
- [ ] VK: тест с обложкой и без неё проверены вручную.
- [ ] Дзен: сессия, редактор, тест с обложкой и без неё проверены вручную.
- [ ] После перезапуска дублей нет.
- [ ] Все `unknown` статусы вручную сверены; неизвестные внешние действия не переотправлялись вслепую.
- [ ] Собрано минимум 10 контролируемых успешных примеров на каждой площадке либо отдельно записано, что блокирует такой прогон.

До выполнения последних пунктов нельзя считать live-интеграцию production-проверенной только на основании зелёного CI.
