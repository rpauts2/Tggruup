# docs/orchestration — активная инженерная очередь

Один файл с выполнимыми заданиями и один проверяльщик к нему. Это не вторая
дорожная карта: продуктовый статус блоков живёт только в
[`docs/EXECUTION_PLAN.md`](../EXECUTION_PLAN.md) (реестр P1…P108), а здесь —
`id`, состояние, владелец, база, разрешённые пути, зависимости и следующее
действие. Ссылки на реестр — поле `p_refs`.

## Зачем

Аудит показал, что планирование жило в двух слабых местах: человекочитаемом
реестре и списке задач, который умирает вместе с сеансом. Отсюда — 87 деревьев
исполнителей, про состояние которых нечего сказать; исполнители, умершие с
незакоммиченной работой и без записи, кто они; и невозможность восстановить,
сколько стоил пакет. Очередь отвечает на три вопроса машиночитаемо: кто владеет
файлом, что можно начать сейчас, и почему именно эта задача стоит.

## Команды

```bash
python tools/queue_check.py                 # 0 согласовано, 1 нарушения, 2 не читается
python tools/queue_check.py docs/orchestration/queue.yaml   # путь можно позиционно
python tools/queue_check.py --ready         # BACKLOG, у которого закрыты зависимости
python tools/queue_check.py --owners        # какие активные задачи чем владеют
python tools/queue_check.py --explain W23-A # что блокирует конкретно эту

# W25-B: заявления ВНЕ очереди — данные передаёт вызывающий, инструмент по-прежнему
# ничего не запускает:
python tools/queue_check.py --foreign-claims "M tgfarm/llm/client.py" \
    --foreign-owner "missions/t1-t4 session"
git -C <основное-дерево> status --porcelain > /tmp/claims.txt
python tools/queue_check.py --foreign-claims /tmp/claims.txt --foreign-owner SESSION

# пакет для приёмки знает, кто ещё держит эти байты (W25-B):
python tools/review_packet.py --base 7e58455 --head w28a-llm-reliability \
    --task W28-A    # --queue <путь> — если queue.yaml ищется не в <repo>/docs
```

## Состояния

`BACKLOG → READY → ASSIGNED → RUNNING → REVIEW → ACCEPTED → INTEGRATED → VERIFIED`,
плюс `BLOCKED`, `FAILED`, `RECOVERY_REQUIRED`, `CANCELLED`, `DEFERRED`.

Проверяльщик отдельно следит за тем, чего человек склонен не замечать:

* **одна задача — одно состояние.** `status: VERIFIED` рядом с
  `integration_status: NOT_INTEGRATED` — это две версии одного факта, и он краснеет;
* **нет места — нет работы.** `RUNNING` без ветки и дерева возможен только для
  `owner_agent: "coordinator"` (иначе запись притворяется исполняемой);
* **пути не пересекаются.** `tgfarm/llm/`, `tgfarm/llm/client.py` и
  `tests/test_w25a_*.py` против `tests/test_w25a_queue.py` — один владелец на
  байты. Задача в терминальном состоянии файлы отпускает;
* **зависимости существуют, ацикличны и закрыты**, иначе `READY` не засчитывается;
* **SHA обязан существовать.** Реестр этой статьи уже содержал агента, назвавшего
  несуществующий коммит. Проверка перечисляет `packed-refs` и свободные ссылки и
  молчит, если перечислить нечего: незнание не переодевается в нарушение. Это
  слабое место названо, а не замолчано — после `git gc` объекты уезжают в паки,
  и честное решение про «существует ли этот коммит» требует `cat-file`, то есть
  запуска процесса, который этому инструменту запрещён. Поэтому полное доказательство
  SHA — задача `tools/review_packet.py`, где чтение git разрешено. С W25-B та же
  проверка работает и в связанном worktree: `.git` — файл-указатель `gitdir:`,
  ссылки лежат в общем каталоге, и `_git_dirs` это различает (раньше внутри
  worktree проверка молчала — именно там и пишутся фейковые SHA).

## Заявления вне очереди (W25-B)

Коллизия W28-A/missions показала слепое место: queue.yaml описывает только
запланированное, а второй сеанс может держать те же байты незакоммиченными в
общем дереве. Инструмент по-прежнему читает и ничего не запускает — список
грязных путей ему передаёт вызывающий (`--foreign-claims`, см. выше). Правила:

* `duplicate-active` — путь одновременно держат активная запись очереди
  (READY…ACCEPTED) и чужой владелец; в тексте названы оба владельца;
* `foreign-claim` — путь грязен у чужого, пока запись в состоянии резерва
  (BLOCKED, RECOVERY_REQUIRED) бережёт его; BACKLOG-планы чужую работу не
  блокируют (намерение — не владение);
* владелец, зарегистрировавший свои пути в очереди (у MISSIONS-T1…T4
  `owner_agent` совпадает с чужим владельцем), не создаёт проблем — проверка
  ищет незарегистрированную реальность, а не двойную бухгалтерию;
* схема полей и словарь состояний не расширены: чужие пакеты живут обычными
  BLOCKED-записями с причиной `uncommitted in the shared main tree`, а
  доказательство в `evidence` получает префикс `GIT_VERIFIED:` со ссылками на
  коммиты (поле — список строк, префикс ничего не меняет в схеме).

Пакет для приёмки (`tools/review_packet.py`) с W25-B печатает OWNER HEADER и
секцию `3c`: какие ещё записи очереди держат изменённые пути. Вердикт остаётся
единственной последней строкой `NEEDS_HUMAN` — инструмент показывает коллизию,
но не разрешает её.

## Планировщик диспетчеризации: `tools/dispatch_plan.py`

Волна 25 подняла девять исполнителей на `cd21f29` — устаревшем кончике
второго remota вместо названной базы `183daa4` (разрыв 253 коммита);
половина из них измерила не то дерево и выдала это за факты о проекте.
Правило в `docs/CONTINUATION_STATE.md` существовало и не было применено —
значит, его должен делать невозможным инструмент.

```bash
python tools/dispatch_plan.py --base <полный-40-символьный-SHA>  # база только явная
python tools/dispatch_plan.py                                    # если записи сами пинят полный base_sha
python tools/dispatch_plan.py --id W24-M --base <SHA>            # только эта запись (состояние обязано быть dispatchable)
python tools/dispatch_plan.py --base <SHA> --foreign-claims "$(git status --porcelain)"
```

Что планировщик гарантирует и чего не делает:

* dispatchable состояния — `DISPATCHABLE` (READY, ASSIGNED), определённые в
  самом планировщике как подмножество словаря `STATES` из `queue_check.py`
  (проверяльщик этот набор не экспортирует): второго конечного автомата здесь нет;
* база никогда не угадывается: только `--base` или полный `base_sha` записи;
  короткая форма (`183daa4`) — это сводка, а не пин, она даёт отказ; два
  несовпадающих названия базы — тоже отказ, а не выбор;
* команда печатается только в форме `git worktree add -b <ветка> <путь> <sha>`:
  без `-b` git читает SHA как имя ветки — дефект, в этом репозитории уже
  записанный однажды;
* пересечения владения — внутри плана, против активных и резервирующих
  записей очереди и против иностранных заявлений (`--foreign-claims`, тот же
  вход, что у проверяльщика) — отказ без единой команды, с именованием пары;
  правила пересечения импортируются из `queue_check`, не дублируются;
* в конце — строка самопроверки: для каждого созданного дерева
  `git -C <путь> rev-parse HEAD` обязано дать ровно закреплённый SHA, а сам
  SHA — заявление, пока `git cat-file -t` не скажет `commit`. Отчёт агента о
  собственной базе — не доказательство; это и есть урок девяти пустых
  отчётов.

Коды выхода: 0 — план напечатан (или очередь не просит диспетчеризации;
честное «нечего планировать» — это ответ, а не пустой план на угаданной
базе), 1 — отказ или пересечение, 2 — вход нечитаем. Сам планировщик ничего
не запускает и ничего не пишет: AST-страж в `tests/test_w26qm_dispatch_plan.py`
проверяет его импорты и вызовы (страж `tests/test_w25a_queue.py` сейчас
покрывает только `queue_check.py`), а поведение закреплено там же, включая
байт-в-байт неизменность queue.yaml после запуска.

## Чего этот инструмент не делает, и это важно

Он ничего не запускает. Ни `subprocess`, ни сокетов, ни записи — правило
закреплено тестом, который читает импорты и вызовы через AST, а не грепом по
тексту (мой же докстринг упоминает `subprocess.run` как объяснение запрета, и
подстрочный поиск спотыкался об это). Инструмент, который умеет только читать,
не сможет притвориться диспетчером, а очередь — автономной системой.

Тесты: [`tests/test_w25a_queue.py`](../../tests/test_w25a_queue.py) — согласованность
живого файла, каждая правило-на-мутанте, кодопад на кириллической консоли и
структурный запрет на запуск; [`tests/test_w25b_review_packet.py`](../../tests/test_w25b_review_packet.py)
— владелецный заголовок пакета, регрессия «два владельца одного client.py» и
честное отсутствие queue.yaml.

Отдельно: [`docs/READINESS_MATRIX.md`](../READINESS_MATRIX.md) — матрица
готовности по четырём разным утверждениям (код / офлайн-тест / доступность
планировщику / наблюдение на живой ферме) с тегом доказательства в каждой
ячейке и приложением команд для пересъёмки. Очередь отвечает на «что делать
дальше», матрица — на «что уже доказано»; при противоречии приоритет у
замеров из матрицы, потому что каждая её ячейка указывает на команду или
строку файла, а не на обещание.
