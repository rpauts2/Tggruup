# Центр площадок TgFarm

Панель «Площадки» — единая точка управления уже подключёнными каналами и будущими интеграциями.

## Нативная редакция и выбор формата

У каждого из 33 направлений есть профиль в `tgfarm/platform_editorial.py`: целевая аудитория, редакторская цель, голос, допустимые форматы, длина, тип адресата и обязательные проверки. Профиль описывает текущий код и не объявляет неподдерживаемый publisher доступным.

В карточке уже опубликованного материала можно выбрать любую площадку и нажать «Собрать нативную версию». Этот preview:
- создаёт отдельный заголовок и текст под формат/аудиторию назначения, когда включён онлайн‑LLM и хватает дневного бюджета; иначе оставляет детерминированный черновик;
- сохраняет исходные URL, не должен придумывать факты, цифры, цитаты или личный опыт;
- показывает адресата и ограничения; для Reddit использует отдельный Scout, для vc.ru и Пикабу повторно читает каталог/правила;
- блокирует формат, если текущему publisher нужно видео/изображение, а такого файла нет;
- preview сам ничего не публикует: API отвечает `publish_action: none`. Это отдельный инструмент подготовки;
- после включения LIVE общий S9 автоматически выбирает подходящие материалы, нативный формат и подключённые площадки, затем отправляет их через рабочие адаптеры;
- TikTok и Douyin остаются отдельными workflow с обязательным индивидуальным согласием; это исключения, а не общий режим всей фермы.

В автоматической очереди общий S9 использует тот же профиль, выбирает формат по реально приложенным медиа и запускает AI-переписывание только в `live` и только через общий AI budget. Reddit, TikTok и Douyin остаются отдельными workflow: они не проходят через общий фоновый переписыватель.

**Важное различие:** редакционный профиль не равен поддержке медиа publisher-ом. Например, текущие адаптеры X/Bluesky/Threads/LinkedIn/Mastodon/MAX/Discord/Tumblr работают с текстом; VK поддерживает текст и фото; YouTube требует видео; Instagram поддерживает одно фото или один Reel; Pinterest, Facebook Pages и OK имеют медиа-пути. Не добавляй галерею, видео или загрузку изображений в профиль, пока соответствующий адаптер реально не умеет это доставлять.

## Выбор назначения после OAuth

Pinterest и Facebook больше не требуют заранее угадывать ID назначения. Сначала владелец настраивает App ID/Secret и проходит официальный OAuth:
- **Pinterest:** TgFarm получает доски через API v5 `GET /boards` в пределах разрешения `boards:read`; UI показывает только ID, имя, описание, privacy и ссылку. После выбора сервер ещё раз вызывает `GET /boards/{id}` с текущим токеном и только тогда сохраняет `PINTEREST_BOARD_ID`.
- **Facebook Pages:** после обмена OAuth-кода TgFarm читает `/me/accounts`, проверяет `CREATE_CONTENT` (либо эквивалентную административную задачу), отбрасывает остальные страницы и не возвращает Page access tokens в список. При выборе сервер повторно проверяет задачу и только затем сохраняет Page access token локально.
- До выбора Page/доски авторизация приложения и право на публикацию в конкретном назначении отображаются как разные состояния. Нельзя считать аккаунт полностью готовым к публикации до выбора целевого места.

Токены не отправляются браузеру. Список назначений может быть пустым, если приложение не получило требуемые scopes, роль/задачу или нужный тип аккаунта.

## MAX: поиск каналов и групп через webhook

MAX не предоставляет готовый API-список всех чатов, куда добавлен бот. TgFarm использует официальный событийный механизм:
1. Владелец сохраняет MAX bot token и задаёт публичный URL в карточке MAX (или `TGFARM_PUBLIC_BASE_URL=https://farm.example` в .env). Это домен reverse proxy, указывающий на TgFarm, с доверенным полным TLS-сертификатом на 443, не localhost.
2. Нажатие «Подключить поиск чатов» создаёт `POST /subscriptions` на `platform-api2.max.ru` для событий `bot_added`, `bot_removed`, `chat_title_changed` и `bot_admin_permissions_changed`.
3. MAX отправляет HTTPS POST на `/api/platforms/max/webhook`. Callback доступен без токена панели, но принимает запрос только с секретом `X-Max-Bot-Api-Secret`, сохранённым локально. Порт должен быть 443, сертификат доверенный и полная TLS-цепочка.
4. После добавления бота в канал или групповой чат приходит `bot_added` с `chat_id` и `is_channel`. События приватного диалога `bot_started` не используются как цели публикации. Удаление бота удаляет адресат из списка.
5. Владелец выбирает найденный чат. TgFarm повторно вызывает `GET /chats/{chatId}/members/me` и требует административное право `write` (либо владение чатом) перед сохранением `MAX_CHANNEL_ID`.
6. Публикация выполняется через `POST /messages?chat_id=...` на `platform-api2.max.ru` с токеном в заголовке `Authorization`, не в URL.

Если бот уже был добавлен до создания webhook, новое событие не возникнет автоматически: удали и снова добавь бота или добавь его в ещё один нужный чат, чтобы MAX прислал `bot_added`. Либо введи известный ID вручную только после того, как API проверил право `write`.

TgFarm не считает найденный ID разрешением на публикацию: каждый сохранённый адресат проверяется повторно, а событие об изменении прав помечает его на новую проверку.

## Авторизация: API и браузер — разные уровни

- VK использует отдельное VKHost OAuth-окно, захватывает только официальный OAuth redirect и сохраняет токен локально. После входа TgFarm получает через `groups.get` список сообществ с ролью администратора/редактора. Выбранное сообщество повторно проверяется перед сохранением ID; publisher отправляет `wall.post` на отрицательный `owner_id`, как требует стена сообщества.
- Дзен открывает отдельный persistent Chrome/Chromium profile. Вход выполняется владельцем; Yandex cookies остаются внутри локального браузерного профиля. При публикации DzenWebPublisher проверяет живую сессию. CAPTCHA не решается и не обходится: процесс останавливается для ручного действия.
- OAuth площадок (X, Reddit, Instagram, Threads, Facebook, LinkedIn, YouTube, TikTok, Pinterest, Mastodon, Tumblr, Douyin) использует отдельные callback/state/PKCE или provider flow. Внешние App ID/Secret и redirect URI всё равно должны быть созданы и настроены владельцем в кабинете площадки.
- MAX, Discord, Bluesky и OK используют типы credentials, предусмотренные их текущими адаптерами.
- Общий browser-login для остальных сайтов хранит изолированный локальный профиль и показывает, удалось ли распознать известную session cookie. Это **не** OAuth-токен и **не** право на автоматическую публикацию. Для неподдерживаемых publishers браузерный вход даёт только сохранённую сессию/подготовку ручного редактора.

Секреты и cookies не возвращаются в UI и не копируются в логи. Не пытайся извлекать токены из недокументированных cookie/localStorage или превращать обычный login в обход официальных разрешений.

## Что означает переключатель

- **Включена**: новые отправки на эту площадку разрешены, если настроены нужные credentials и сама платформа принимает запросы.
- **Выключена**: новые отправки блокируются; запланированные записи не удаляются и остаются в очереди. После включения они снова смогут отправиться.
- **Нужна настройка**: маршрут поддерживается кодом, но в файле .env отсутствуют обязательные ключи или не найден профиль.
- **В плане интеграций**: приоритет выбран, но рабочего адаптера пока нет. Эта метка не включает публикацию и не создаёт fake-success статусы.

Переключатель не обрывает запрос, который уже передан внешней площадке. Уже начатая отправка может завершиться. Неизвестный результат по-прежнему требует ручной сверки, автоматический дубль не запускается.

## Что мы уже знаем про правила назначения

Ответ на вопрос «под какими правилами мы опубликовали» лежит в таблице `community_policy_snapshots`, а не в самом механизме перечитывания. Команда перечитывания — шаг обслуживания `watch_destination_rules` — открывает площадку (Reddit, Пикабу) и дописывает снимок в историю. Читать ради этого сеть нельзя, поэтому только чтение вынесено в отдельную команду:

```
python -m tgfarm.cli rules-status [--format text|markdown] [--platform ID] [--target ID] [--history-limit N]
```

Она ничего не отправляет, ничего не перечитывает и ничего не записывает: выводятся переключатели площадок и уже сохранённые снимки (назначение, `rules_hash`, возраст снимка, вердикт, причина состояния). Текст, пришедший с площадки, остаётся неинструкцией: он проходит ту же обработку, что и история для панели (управляющие символы сведены, длина ограничена, токеноподобные фрагменты вырезаны). Возраст считается из сохранённого `checked_at`; если снимка нет, в этом месте стоит «нет снимка правил», а не `0 ч` и не пустая строка (P34). `--history-limit` ограничивает число названных назначений (не больше 200, как у панели); если разрез получился, строка это говорит.

Состояния — те же слова, что у шага перечитывания, чтобы не появляется второй диалект. Включено ли наблюдение, решает один предикат — `maintenance.rules_watch_switch`, вызываемый и шагом, и этой командой, а не две его копии:

- `disabled` — решение оператора: площадка выключена в центре площадок, её правила не читаются и история не пополняется.
- `enabled_no_known_destination` — решения ещё нет: наблюдение за площадкой включено и читатель правил есть, но история не называет ни одного назначения, поэтому перечитывать нечего; первое назначение появится из выбора цели или публикации. Это отдельная строка именно потому, что выключенная площадка и невключённое назначение — разные факты.
- `watched` — наблюдение включено, читатель правил есть, история называет назначения. Слово означает те же условия, которые шаг перечитывания проверяет до первого запроса; сама эта команда ничего не перечитывала, счётчиков прогона у неё нет.
- `no_rules_reader` — история называет площадку, для которой в коде TgFarm читателя правил ещё нет. Это наша лакуна, а не отсутствие правил у площадки; в `RULES_WATCH_PLATFORMS` сейчас `pikabu`, `reddit` и `vc_ru` (назначение vc.ru читателем обеспечивает `community_targets.read_vc_topic_rules`), поэтому лакуна здесь — про новую площадку, которой ещё нет в списке.
- `nothing_to_watch` — итог, когда ни одна площадка не дошла до `watched`: переключатели выключены либо история не называет ни одного назначения.

Площадка без переключателя — отдельный случай, и он реальный: `vc_ru` `draft_only`, ключа `enabled.vc_ru` в центре площадок нет, поэтому у такой строки нет ни поля `switch`, ни поля `enabled` — команда не обещает переключатель, которого не существует. Скажемое вслух: раньше это место печатало `disabled (переключатель enabled.vc_ru)`, то есть отказывало работающему читателю и звало оператора переключать несуществующий ключ.

Измеренный срез 2026-11-05: `SELECT COUNT(*) FROM community_policy_snapshots` на живой базе — 0, `enabled.reddit: false`, ключа `pikabu` в `config/platforms.yaml` нет. То есть боевой путь этой команды сейчас — пустой: она обязана назвать состояние и причину, а не напечатать пустую таблицу. Реально перечитывают правила и дописывают историю шаг обслуживания (`tgfarm maintain`, общий цикл) и карточка «История правил» в панели; здесь только то, что уже лежит.

## LinkedIn: OAuth и нативная публикация

Для подключения создай приложение в [LinkedIn Developer Portal](https://www.linkedin.com/developers/) и добавь продукты **Sign In with LinkedIn using OpenID Connect** и **Share on LinkedIn**. В карточке площадки нажми «Настроить приложение» и сохрани Client ID/Client Secret. Затем нажми «Подключить через OAuth», скопируй callback URI из окна подтверждения и добавь его в Authorized redirect URLs в кабинете LinkedIn. Запрашиваются только `openid`, `profile` и `w_member_social`; разрешение публикации доступно лишь когда его выдал LinkedIn для приложения.

TgFarm использует authorization-code flow с одноразовым случайным `state`, обменивает код на пользовательский access token и проверяет профиль через OpenID Connect `userinfo`. Коды и токены не возвращаются в браузер и удаляются из callback query string до access-логирования. Учётные данные хранятся в локальном `.env`. Если LinkedIn выдал refresh token, TgFarm пытается обновить истекающий access token и сохраняет ротированные значения; если refresh token не выдан, после истечения срока потребуется повторно подключить аккаунт.

Для публикации используется `POST https://api.linkedin.com/rest/posts` с заголовками `LinkedIn-Version: 202610` и `X-Restli-Protocol-Version: 2.0.0`. Текущая реализация публикует только текст от имени подключённого участника, без изображений, видео и публикаций от имени организации. После принятия публикации сохраняется `x-restli-id`; если LinkedIn не вернул ID, результат остаётся неопределённым, чтобы ферма не создала возможный дубль автоматически.

LinkedIn выключен по умолчанию. После успешного OAuth включи площадку вручную и сначала сделай один тестовый пост, который можно удалить. Реальная возможность публикации зависит от доступа приложения к продукту и разрешению `w_member_social`, а также актуальных правил, версий и лимитов LinkedIn API.

## Threads: OAuth и публикация текстовых постов

Для подключения нужен Meta Developer App с добавленным продуктом Threads API. В карточке Threads нажми «Настроить приложение», сохрани **Threads App ID** и **Threads App Secret**, затем нажми «Подключить через OAuth». Перед подтверждением добавь показанный callback URL в Threads API → OAuth Redirect URIs и разреши `threads_basic` и `threads_content_publish`. В режиме разработки подключаемый аккаунт должен быть добавлен к ролям/тестерам приложения; доступ к API зависит от состояния и проверки самого Meta App.

TgFarm обменивает одноразовый OAuth-код на краткоживущий токен, затем запрашивает долгоживущий пользовательский токен и проверяет профиль через `GET /v1.0/me`. Код, state и токены не возвращаются в браузер и очищаются из query string до access-логирования. Токен сохраняется в локальном `.env`; при приближении срока окончания он обновляется через Threads API. Публикация использует двухшаговый процесс: создать текстовый контейнер `/threads`, затем отправить его через `/threads_publish`. После успешной отправки TgFarm старается получить permalink.

Поддерживается текстовая публикация; фото, видео и карусели здесь пока не реализованы. Threads выключен по умолчанию, поэтому после успешного OAuth сначала включи площадку и протестируй одну публикацию на собственном аккаунте. Внешний Meta App, его redirect URI, разрешения и режим доступа должны быть настроены на стороне владельца приложения.

## Bluesky: подключение и публикация

Bluesky добавлен как рабочий адаптер AT Protocol для коротких текстовых постов. В карточке сети введи handle (например, `name.bsky.social`) и **app password**, созданный в Settings → Privacy and Security → App passwords. Не используй основной пароль аккаунта. TgFarm получает краткоживущую сессию через `com.atproto.server.createSession` и создаёт запись через `com.atproto.repo.createRecord`; пароль не возвращается в UI и не попадает в логи. Поддерживается текст, не видео/карусели; длина текста ограничивается безопасным базовым пределом. Bluesky выключен по умолчанию: после проверки авторизации включи его в каталоге и сначала проверь публикацию на собственном аккаунте в режиме `live`.

## Mastodon: вход через OAuth 2.0 + PKCE

В карточке Mastodon нажми «Подключить через OAuth» и укажи адрес своего сервера, например \`https://mastodon.social\`. TgFarm зарегистрирует OAuth-приложение на выбранном инстансе, откроет страницу согласия и запросит только \`read\` и \`write:statuses\`. Пароль Mastodon не вводится и не сохраняется: после согласия приложение получает пользовательский токен и проверяет профиль через \`accounts/verify_credentials\`. Код возврата и OAuth state не попадают в сообщения журнала; callback захватывает только необходимые параметры и очищает query string до вызова обработчиков. Токен и client secret сохраняются локально в \`.env\`. Mastodon выключен по умолчанию.

Адаптер публикует текстовые статусы, ограничивает тело 500 символами как безопасным базовым лимитом и передаёт \`Idempotency-Key\`, поддерживаемый Mastodon для защиты от дублирующих запросов. Сначала включи площадку и проверь одну тестовую публикацию на собственном аккаунте. На старых инстансах PKCE может быть недоступен, поэтому подключение требует современный Mastodon с поддержкой PKCE.

## X: OAuth 2.0 для пользовательской публикации

Старый app-only Bearer token подходит для части read-запросов, но сам по себе не является пользовательским разрешением на создание постов. Поэтому публикация X переведена на OAuth 2.0 Authorization Code + PKCE: TgFarm запрашивает только \`tweet.read\`, \`users.read\`, \`tweet.write\` и \`offline.access\`, получает профиль через \`/2/users/me\` и сохраняет access/refresh-токены в локальный \`.env\`. Пароль X не запрашивается. Access token обновляется по refresh token, включая сохранение нового refresh token, когда X его ротирует.

Перед подключением создай приложение в [X Developer Portal](https://developer.x.com/), включи OAuth 2.0, выбери confidential/Web App тип клиента и скопируй Client ID и Client Secret в «Настроить приложение» в TgFarm. При нажатии «Подключить через OAuth» панель покажет точный Callback URI: добавь его в настройки X до продолжения. Callback обрабатывает одноразовый state, использует PKCE и очищает query string до access-логирования, так как X рекомендует не журналировать authorization code. Публикация остаётся отключённой в настройках до ручного включения и проверочной публикации.

Текущая X API доступность и цена зависят от проекта и лимитов на стороне X. TgFarm не обходит эти ограничения; при ошибке публикации проверь доступ к endpoint создания поста и разрешение \`tweet.write\`.

## Авторизация площадок в панели

В каждой карточке площадки есть отдельная область подключения. Она различает:
- **Доступ подтверждён** — TgFarm выполнил read-only запрос к API либо проверил браузерную сессию, и площадка ответила успешно.
- **Данные сохранены, нужна проверка** — обязательные настройки обнаружены, но их ещё не проверили реальным запросом.
- **Проверка не пройдена** — последние сохранённые учётные данные отклонены или сессия не авторизована.
- **Интеграция пока не подключена** — кнопка открывает сайт для ручного входа/настройки аккаунта, но публикация в TgFarm не реализована.

Кнопки не запрашивают пароль пользователя от соцсети в TgFarm и не обещают OAuth там, где он ещё не написан. Для встроенных адаптеров токены можно записать из панели: вводимые значения сохраняются в локальный `.env`, секреты никогда не отправляются обратно на клиент и не включаются в журнал. Пустое поле означает «не изменять сохранённое значение». Замена ключа сбрасывает старый подтверждённый статус до повторной проверки. Файл обновляется атомарно; права ограничиваются до `0600` там, где ОС поддерживает chmod. Храни `.env` вне Git и резервных копий, которые кому-то доступны.

Для Telegram проверка подтверждает token через `getMe`, но не проверяет право бота публиковать в конкретный канал. Для VK, MAX и X проверяется доступ к данным профиля/сообщества, а не write-доступ. Для Reddit проверяется OAuth и чтение выбранного subreddit; scope `submit` и первая публикация проверяются отдельно. Только контролируемый smoke-test может подтвердить фактическую публикацию.

Для Дзена кнопка открывает рабочее headed-окно входа в Яндекс и сохраняет сессию в выделенный профиль браузера. Для социальных сетей без адаптера кнопка лишь открывает сайт и сообщает об ограничении. Когда API-адаптер появится, его проверка должна быть реализована отдельно.

## Reddit: первый рабочий адаптер

- Публикует нативный текстовый пост по умолчанию; для контролируемого workflow возможен link-пост.
- В LIVE S9 Scout ищет до восьми подходящих сообществ, читает доступные правила и требования, адаптирует материал и перед отправкой повторно проверяет выбранный subreddit. В публикацию уходит один выбранный subreddit, а не массовая рассылка.
- Идентификатор, URL и состояние отправки сохраняются в общем журнале кросспостинга. Неопределённый результат не запускает автоматический повтор, чтобы не создавать дубль.
- Адаптер требует `REDDIT_CLIENT_ID`, `REDDIT_CLIENT_SECRET`, `REDDIT_REFRESH_TOKEN`, `REDDIT_USER_AGENT` и явного `REDDIT_API_APPROVED=true` после получения разрешённого доступа к Data API. `REDDIT_SUBREDDIT` необязателен: при пустом значении цель подбирает Scout. Используй OAuth с разрешением `submit` и permanent refresh token; пароль аккаунта не хранится.
- Глобальный переключатель по умолчанию выключен. Сначала проверь, что Reddit разрешил твоему приложению API-доступ, и выполни одну тестовую публикацию в сообщество, где правила действительно допускают такой контент.
- Внизу панели есть Scout: поиск до восьми сообществ, оценка совпадения, чтение доступных правил/технических ограничений и отдельный редакторский черновик на базе опубликованного поста.
- Перед отправкой сервер повторно сверяет машинно-читаемые ограничения; если обязателен flair, который UI ещё не умеет выбирать, публикация блокируется.
- Адаптер не публикует комментарии, не ставит голоса, не отправляет личные сообщения и не рассылает один пост массово по разным subreddit. Следуй правилам конкретных сообществ и ограничениям Reddit API.

Официальная документация: [Reddit API](https://www.reddit.com/dev/api/) и [правила Data API](https://support.reddithelp.com/hc/en-us/articles/16160319875092-Reddit-Data-API-Wiki). Пошаговая настройка: [REDDIT_SETUP.md](REDDIT_SETUP.md).

## Метрики и обучение Reddit Scout

В секции Scout появилась кнопка обновления статистики и карточки результатов по сообществам. Для подтверждённых Reddit-постов собираются только доступные через стандартный Data API поля: score, число комментариев и upvote ratio. Срезы сохраняются во временной ряд; повторное нажатие в пределах 15 минут обновляет последний срез, а не создаёт новый. Обход ограничен 100 публикациями за запрос, кнопка собирает до 50.

Scout использует историю TgFarm как небольшой ограниченный бонус к тематическому совпадению. Размер выборки показан отдельно; малое число постов не трактуется как достоверный сигнал. Если данных нет, рейтинг продолжает работать на описаниях/активности сообществ. Просмотры и показы из этого API-запроса не предполагаются и не подставляются синтетически. Метрики никогда не меняют статус публикации и не запускают повторный пост.

## Telegraph: автономные long-form статьи

Telegraph входит в общий S9 как отдельная статья, а не как короткий mirror поста. Создай аккаунт официальным методом createAccount и сохрани access_token в поле TELEGRAPH_ACCESS_TOKEN карточки площадки. Проверка доступа вызывает read-only getAccountInfo.

При публикации TgFarm преобразует Markdown-подмножество в нативные Telegraph Node: заголовки, абзацы, списки, цитаты, код и ссылки. Перед запросом проверяется ограничение API в 64 KiB для сериализованного массива content; заголовок ограничен 256 символами. S9 использует отдельный редакторский профиль и собственный дневной лимит, а результат сохраняет page path/URL в общем журнале. Неопределённый ответ после createPage помечается как unknown и не отправляется повторно автоматически.

Официальная документация: https://telegra.ph/api.

## Discord: webhook публикация

Discord включён как рабочая цель S9 для принадлежащих владельцу серверов и каналов. Вставь `DISCORD_WEBHOOK_URL` из настроек канала. TgFarm проверяет webhook read-only запросом `GET` и не посылает тестовых сообщений при проверке. Публикация использует `wait=true`, чтобы получить подтверждённый message ID; `allowed_mentions.parse` пуст, поэтому сообщения фермы не вызывают `@everyone` и массовые mentions. Для форумных каналов требуется конкретный `thread_id` в метаданных назначения; автоматический выбор ветки пока не включён.

Webhook URL фактически является секретом доступа к каналу: храни его только в локальном `.env`, не вставляй в скриншоты и при утечке сразу перевыпусти webhook в Discord.

## Одноклассники: REST API групповых медиатопиков

Одноклассники подключаются через официальный REST API. TgFarm подписывает каждый запрос MD5 по правилам OK: сортирует параметры по ключу, исключает `access_token`, добавляет session secret и отправляет запрос на `https://api.ok.ru/fb.do`. Поддерживаются текстовые групповые медиатопики, фото и видео. См. [mediatopic.post](https://apiok.ru/dev/methods/rest/mediatopic/mediatopic.post), [photosV2.getUploadUrl](https://apiok.ru/dev/methods/rest/photosV2/photosV2.getUploadUrl), [video.getUploadUrl](https://apiok.ru/dev/methods/rest/video/video.getUploadUrl) и [video.update](https://apiok.ru/dev/methods/rest/video/video.update).

В настройках приложения запроси у `api-support@ok.ru` разрешения `VALUABLE_ACCESS`, `LONG_ACCESS_TOKEN`, `GROUP_CONTENT`, `PHOTO_CONTENT` и `VIDEO_CONTENT`. Пользовательский `LONG_ACCESS_TOKEN` действует 30 дней и автоматически продлевается при использовании API. В карточке TgFarm введи Application Key, Application Secret, access token и ID группы. `OK_SESSION_SECRET_KEY` можно заполнить, если он выдан вместе с токеном; иначе подпись вычисляется по официальному fallback MD5(access_token + application_secret_key). Секреты сохраняются только в локальном `.env`.

Проверка авторизации read-only подтверждает текущего пользователя, выбранную группу и `GROUP_CONTENT`; наличие `PHOTO_CONTENT` и `VIDEO_CONTENT` показывается отдельно. Для фото TgFarm получает upload URL через `photosV2.getUploadUrl` и прикладывает upload token непосредственно к групповому медиатопику. Для видео используется `video.getUploadUrl`, multipart upload и завершающий `video.update` перед созданием темы. Ответ `mediatopic.post` с ID `0` теперь считается отказом приложения в публикации, а не успешным постом. Неопределённый ответ после отправки блокирует автоматический повтор до ручной сверки. Переключатель выключен по умолчанию: сначала проверь доступы и сделай один контролируемый пост в тестовую группу.

## Pinterest: OAuth и image/video Pins

Pinterest включён как рабочая цель S9 для image и video Pins. Подключи приложение через Pinterest OAuth с разрешениями `boards:read`, `pins:read`, `pins:write`, заранее укажи ID доски и заверши авторизацию. Callback проверяет, что подключённый пользователь действительно имеет доступ к выбранной доске. Access и rotating refresh token хранятся в локальном `.env`; access token обновляется автоматически до истечения.

Для image Pin ферма использует собственную JPEG-обложку поста и `POST /v5/pins` с `media_source.source_type=image_url`. Для video Pin адаптер регистрирует медиа через `POST /v5/media`, загружает multipart на выданный URL, опрашивает статус до `succeeded` и только потом создаёт Pin с `media_source.source_type=video_id` и обложкой. Pinterest забирает изображение-обложку по короткоживущей HMAC-ссылке `/public/instagram-media/{id}` на публичном HTTPS-домене `TGFARM_PUBLIC_BASE_URL`. Переключатель выключен по умолчанию; сначала выполни один контролируемый пост и проверь его в самой доске.

## Ручная передача на площадки без publisher API

В карточке поста есть блок «Ручная подготовка для остальных площадок». Он собирает 14 направлений: VK Клипы, RUTUBE, vc.ru, Хабр, Пикабу, TenChat, Medium, WhatsApp Channels, Twitch, Snapchat, WeChat, Douyin, RedNote/Xiaohongshu и TikTok. Для Пикабу, Medium и WeChat пакет — запасной путь при наличии автопубликации; для TikTok и Douyin — единственный путь без отдельного согласия владельца.

Пакет содержит адаптированный заголовок и текст (длина не больше `max_chars` профиля редакции площадки), теги, исходные ссылки, локальные ссылки скачивания готового медиа и инструкции для редактора конкретной площадки. Для видеоплощадок отсутствие MP4 отмечается до передачи; можно сначала создать ролик в TgFarm. API `GET /api/platform-drafts/{platform}/{post}/package` ничего не публикует и не меняет статус поста. После проверки владелец сам открывает редактор, загружает файл и нажимает кнопку публикации на стороне площадки.

Это не маскировка API-адаптера. VK Clips и RUTUBE требуют отдельного подтверждённого upload/publish API; у Хабра публичного API создания статей нет; WhatsApp Channels нельзя публиковать через WhatsApp Business Messaging API. Для Medium это именно ручной экспорт: API больше не выдаёт новые integration tokens. Площадки без проверенного и разрешённого способа отправки остаются вне автоматической очереди S9. Пикабу является отдельным исключением: S9 использует подтверждённую сессию владельца и штатный редактор отложенной публикации, не обходит CAPTCHA и блокировки и переводит неоднозначный результат в ручную сверку.

### Следующая очередь: P1

1. **YouTube / Shorts**. Интеграционный слой уже реализован: Google OAuth, refresh token, проверка связанного канала и resumable upload через [YouTube Data API](https://developers.google.com/youtube/v3/docs/videos/insert). Видео загружается с приватностью `private` по умолчанию; настройка аудитории не должна автоматически повышаться до публичной. Адаптер включён как доступная интеграция, но выключен в конфигурации по умолчанию. Перед эксплуатацией нужны действительные Google credentials, доступ к YouTube Data API и контролируемая тестовая загрузка.
2. **TikTok**. Direct Post publisher уже реализован, но не запускается фоновым кросспостером: перед отправкой каждого ролика TgFarm повторно читает creator privacy options и требует отдельного согласия владельца. Для подключения нужен [Content Posting API](https://developers.tiktok.com/products/content-posting-api/), scope `video.publish` и допуск приложения. До аудита приложения публикации могут быть ограничены приватным просмотром.
3. **VK Клипы**. Отдельная интеграция, не синоним обычной записи в стену и не гарантированный побочный эффект `video.save`. Нужно подтвердить официально поддерживаемый clip-specific сценарий загрузки/публикации, права сообщества и обработку результата, прежде чем включать live-режим.
4. **RUTUBE**. Видео и клипы, после подтверждения актуального официального способа загрузки.

### Вторая очередь: P2

- **vc.ru**, **Хабр**: отдельные статьи с отдельной редакторской проверкой; для vc.ru автоматическая публикация пока не включена, поскольку надёжный разрешённый publisher API не подтверждён.
- **TenChat**: деловые публикации с отдельной редактурой.

### Третья очередь: P3

- **WhatsApp Channels**: проверять отдельно. WhatsApp Business Messaging API не следует путать с API управления Channels.
- **Пикабу**: автоматический подбор одного подходящего сообщества, проверка правил и тегов, затем постановка в штатную отложенную очередь. Это статус «запланировано», а не подтверждение публичной публикации; при CAPTCHA или неоднозначном результате автоматизация останавливается.
- **Twitch**: анонсы трансляций и клипы, отдельный сценарий, не обычный постинг.
- **Snapchat**: вертикальные видео при наличии доступа к нужному продукту публикации.
- **WeChat/Weixin**, **Douyin**, **RedNote/Xiaohongshu**: региональные интеграции; потребуют отдельной стратегии, локализации и проверки доступов.

## Почему приоритет такой

Для русскоязычной аудитории разумно сначала довести VK, Telegram, MAX, Дзен и видео-маршруты YouTube/TikTok/VK Клипов/RUTUBE. Для международного охвата уместны Reddit, YouTube, TikTok, Instagram, Threads, Facebook Pages, LinkedIn, Pinterest и Bluesky. Reddit уже подключён как кросспост-адаптер, но включать его следует только после проверки OAuth и правил выбранного subreddit.

Это стартовый приоритет, а не универсальный рейтинг популярности. Приоритет стоит менять под географию, тематику, аудиторию и фактические результаты конкретных каналов.

## Как добавить новый адаптер правильно

1. Проверить актуальную официальную документацию, разрешения приложения и правила публикации.
2. Реализовать самостоятельный адаптер с форматированием, медиа, ограничениями, rate-limit и классификацией ошибок.
3. Сохранить remote ID/URL и идемпотентность. После timeout нельзя повторять отправку вслепую.
4. Добавить offline-тесты и тесты ошибок; новая площадка остаётся в режиме «план» до завершения проверки.
5. Выполнить одну контролируемую live-публикацию, сверить её вручную, затем постепенно наращивать объём.

Состояние каталога хранится в config/platforms.yaml. Секреты и токены в этот файл не записываются: держи их в .env или секрет-хранилище.


## Douyin: ручное создание видео через Open Platform

Douyin использует отдельный Open Platform API, не TikTok Content Posting API. TgFarm подключает Web App через authorization-code OAuth с разрешениями user_info и video.create. Секреты и пользовательские токены хранятся только локально в .env.

Для каждого поста нажми «Подготовить Douyin», просмотри оригинальный MP4 и подпись (до 1000 символов), затем отдельно подтверди создание видео. Скрытого фонового автопостинга нет. TgFarm загружает видео через /video/upload/, затем вызывает /video/create/. Официальный API рекомендует chunk upload для файлов свыше 50 MB; текущая одиночная загрузка ограничена 50 MiB. После создания видео проходит модерацию и временно может быть видно только автору. Если ответ при создании не получен, состояние становится unknown, повторная отправка блокируется до ручной сверки.
