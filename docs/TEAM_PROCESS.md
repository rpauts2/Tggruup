# TEAM_PROCESS — процесс координатора разработки TgFarm

Онбординг координатора, 2026-11-06. Файл описывает, как координатор распределяет работу
между агентами и принимает результаты. Не заменяет `docs/EXECUTION_PLAN.md` (реестр работ) —
дополняет его процессной частью.

## 1. Реальные возможности среды (проверено 2026-11-06)

| Возможность | Статус |
|---|---|
| Субагенты (read-only исследования) | Есть (`spawn_subagent`); квота может исчерпываться — 2026-11-06 все три помощника вернули `402 quota_exhausted` |
| Выбор модели помощника | Есть параметр; модель сильнее ведущей запрещена платформой («GPT 6 Luna» отклонён: только легче или равная) |
| Параллельное исполнение | Несколько помощников в одном ответе; независимые правки/проверки — через пакетные вызовы (`wave`) |
| Долгоживущие AI-сессии, агент-агент сообщения, диспетчер задач | НЕТ. Только субагент-одиночка «задача → отчёт» |
| Git worktree через инструменты координатора | НЕТ (git-инструмент без worktree/merge/pull). Worktree используют агенты Qoder (`.qoder/worktrees`), интеграцию делает координатор |
| Планировщик/cron между сессиями | НЕТ. Фон только внутри сеанса (`run_background`) |
| Сохранение контекста | `docs/EXECUTION_PLAN.md` (волны/пакеты), Project Brain (факты), `read_conversation`, этот файл |

## 2. Роли (логические профили, не отдельные модели)

Каждая роль — это инструкция, которую координатор кладёт в бриф субагента/пакета.

- **Координатор** (ведущая модель): архитектура, декомпозиция, контракты между пакетами, швы-потребители (`api.py`, `cli.py`, `app.js`), приёмка, интеграция, финальный замер.
- **Backend Engineer**: Python, SQLAlchemy/SQLite, очереди, состояния, планировщики. Не трогает UI и адаптеры.
- **Platform Integration Engineer**: адаптеры площадок, OAuth, правила сообществ (`community_policy`, `community_targets`). Не трогает план/очередь.
- **AI/LLM Engineer**: провайдеры, редакционные агенты, промпты, бюджеты, таймауты. Не трогает публикацию.
- **Frontend Engineer**: `tgfarm/ui/app.js`, панели, отображение состояний. Не трогает серверные контракты (их меняет координатор).
- **QA Engineer**: тесты, регрессии, контракты. Исполнитель НЕ запускает проектный набор тестов — полный прогон делает координатор.
- **Independent Reviewer**: читает чужой пакет (не свой), ищет расхождение диф↔заявленное, не повторяет выводы исполнителя.
- **Security/Reliability Engineer**: секреты в логах, идемпотентность, восстановление, watchdog, бэкапы.
- **DevOps/Release Engineer**: CI, Windows-сборка (PyInstaller), git-интеграция.
- **Product/Documentation Analyst**: EXECUTION_PLAN, матрицы готовности, критерии приёмки.

Постоянные ограничения исполнителя (с 2026-11-03, подтверждено практикой волн): не запускать
проектные тесты/git/сборку/серверы; не менять существующие тесты, `conftest.py`, приёмочные фикстуры;
не ослаблять проверки ради зелёного результата; xfail и ошибки не прятать.

```

Контекст: <2–4 предложения + точные файлы для чтения>
Владелец: <роль>
Разрешено менять: <список файлов/каталогов>
Запрещено: <соседние модули, существующие тесты, conftest.py>

Отчёт: список коммитов + что проверено; «готово» без дифа не принимается
```

## 4. Процесс (12 шагов)

1. Координатор: проблема → ожидаемый результат. 2. Проверка зависимостей и base SHA.
3. Назначение владельца. 4. Бриф по шаблону. 5. Агент исследует свою зону и реализует.
6. Агент коммитит по шагам. 7. Координатор перечитывает `git log base..ветка` ПОСЛЕ уведомления
о завершении (урок волны 19: агент коммитит и после приёмки первых коммитов).
8. Независимый ревьюер проверяет контракт. 9. QA/координатор запускает полный набор.
10. Приёмка или возврат. 11. Статус в EXECUTION_PLAN (`todo/in_progress/blocked/implemented/verified`).
12. Свободному агенту — следующий готовый пакет.

Правило швов (из волн 16–22, подтверждено трижды): агент доводит свой модуль до зелёных тестов,
но потребитель контракта в центральном файле остаётся на литералах. Координатор сам grep-ом ищет
читателя нового контракта и закрывает шов. Приёмка = три замера до чтения дифа:
`git cat-file -t <sha>` + `git log base..ветка` + `git -C worktree status --porcelain`.

## 5. Контроль качества приёмки

- Полный прогон только на стабильном дереве без параллельных редакторов (`python -m pytest -q --tb=line`),
  число тестов фиксируется в EXECUTION_PLAN с логом.
- Мутационная проверка ключевых фиксаций: временно сломать защищаемое поведение — тест обязан покраснеть.
- «Готово» принимается только по фактическим коммитам и измерению, не по докладу.
- Базовые ориентиры: 2026-11-06, HEAD `310d9c3` — **3144 passed, 4 xfailed, 12 warnings**.
