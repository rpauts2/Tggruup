# Глобальный план развития TgFarm

Дата обновления: 28.10.2026

> Статус на 28.10.2026: пакеты PR #11 и PR #12 объединены в `main`, CI прошёл. Добавлены проверяемые SQLite-бэкапы, предохранитель импорта истории, безопасный offline demo, runbook VK/Дзен, улучшенное сопоставление тем, проверка provenance источников и двухнедельный порог аналитики. Реальные live-публикации, восстановление пользовательской БД, проверка 20 настоящих тем и качество на реальных материалах остаются операторскими приёмочными шагами.

Цель: сначала довести текущие маршруты публикации до предсказуемой работы, затем превратить TgFarm в автономную редакционную систему, которая помнит свою историю, умеет проверять продолжения тем и улучшает решения на реальных метриках.

## Принцип работы

1. Одна основная ветка — `main`. Изменения объединяем небольшими проверяемыми блоками, а не создаём новую ветку для каждой мелкой правки.
2. Код считается готовым только после CI. Интеграцию с реальными аккаунтами дополнительно проверяем отдельно, с минимальным контролируемым прогоном.
3. Не добавляем новые площадки и сложные AI-функции, пока базовая доставка и восстановление после ошибок не подтверждены.
4. Никаких автоматических повторов, если площадка могла уже принять публикацию. Неопределённый результат должен требовать сверки, а не создавать дубль.
5. История публикаций и старые факты помогают найти контекст, но сами по себе не являются доказательством актуального факта.

## Ближайшие действия после текущего пакета

1. Дождаться зелёного CI Reddit-адаптера; перед live-публикацией заполнить OAuth-параметры локально и проверить правила выбранного subreddit.
2. На своей базе выполнить `tgfarm backup`, затем предпросмотр истории без `--apply`; только после сверки добавить небольшой пробный импорт.
3. Провести контролируемые live-прогоны VK и Дзена по [smoke-test инструкции](docs/SMOKE_TEST_VK_DZEN.md), начиная с одного материала, а затем довести статистику до 10 проверенных примеров на площадку.
4. Проверить 20 реальных досье тем и 50–100 собственных материалов для quality-регрессии.
5. Собрать метрики не менее двух недель и проверить сопоставление каждой метрики с конкретной публикацией.
6. Только после этого переходить к расширению платформ и коммерциализации.

**Запрет на расползание работ:** не начинать параллельно новые платформы, многопользовательский SaaS, ночную эволюцию промптов и сложные агентные схемы, пока критерии первых пяти этапов не выполнены.

# План полной прокачки TgFarm — последовательная программа

Правило исполнения: закрываем один этап, фиксируем код и тесты, проверяем доступный CI, обновляем этот список и только потом переходим к следующему. Реальные аккаунты и секреты не имитируем; live-публикации выполняются только на аккаунтах владельца и по одному контролируемому материалу. Нельзя обещать результат теста, который фактически не запускался.

## Фаза A. Целостность и безопасность

- [ ] A1. Проверить текущий HEAD, рабочую документацию, CI и отсутствие дублирующих открытых PR.
- [ ] A2. Проверить все точки входа API: авторизация, localhost по умолчанию, запрет секретов в ответах/логах, защита опасных действий.
- [ ] A3. Проверить SQLite backup/restore на временной базе, миграции и запуск после аварийного завершения.
- [ ] A4. Закрепить regression-набор: unit, API, UI JavaScript, offline end-to-end и сценарии ошибок.
- [ ] A5. Пройтись по зависимостям и настройкам сборки Windows/VPS, обновить инструкции установки и диагностики.

**Выход:** чистый и проверяемый базис; ни одна интеграция не считается рабочей только по наличию класса адаптера.

## Фаза B. Центр авторизации и подключений

- [ ] B1. Единая карточка каждой площадки: статус подключения, способ авторизации, обязательные поля, тест соединения, последняя проверка.
- [ ] B2. Где поддерживается официальный OAuth: кнопка «Подключить» открывает настоящий поток авторизации, callback проверяет state/PKCE, токены сохраняются безопасно.
- [ ] B3. Где OAuth нет: поля только для реально нужных ключей/паролей приложения; секреты маскируются и никогда не возвращаются API.
- [ ] B4. Разделить «данные заполнены», «авторизация проверена», «публикация проверена» и «площадка включена».
- [ ] B5. Обновление/отзыв токена, понятные ошибки, повторная проверка и инструкции для пользователя.

**Выход:** интерфейс честно показывает подключение каждой сети и не изображает успешную авторизацию без реального ответа платформы.

## Фаза C. Единый центр публикаций

- [x] C1. Единая карточка материала с состояниями доставки по всем площадкам (группировка по материалу добавлена в панели).
- [x] C2. В истории каждой площадки показывать статус, попытку, время, ошибку, remote ID и ссылку на публикацию.

- [x] C4. Ручная сверка неопределённого результата; повтор недоступен без подтверждения отсутствия поста (проверено по API-контракту и защитам повторной отправки).

**Выход:** оператор видит судьбу одного материала целиком, а не собирает её по нескольким разрозненным спискам.
